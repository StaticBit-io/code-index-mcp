## 1. Задача

Заменить широкие текстовые заходы (`Grep`/`Glob`) при работе Claude Code с крупной C#-кодовой базой на семантический поиск по локально построенному векторному индексу.

Мотив — стоимость. Фаза «найти нужное место» съедает бо́льшую часть входного контекста сессии: несколько заходов `Grep` с десятками ложных совпадений, затем чтение файлов вслепую, чтобы понять, тот ли это класс. Каждый лишний файл остаётся в контексте до конца сессии и подаётся заново при каждом запросе.

Эмбеддинги считаются локально и бесплатно. Ожидаемый эффект — сокращение входных токенов на поисковоёмких сессиях примерно на треть-половину, плюс меньше итераций из-за ошибочных направлений.

**Важное ограничение ожиданий:** индекс экономит *поиск*, а не *работу*. Если задачу нельзя решить, не прочитав восемь файлов целиком, их всё равно придётся прочитать. Выходные токены не меняются вовсе.

## 2. Область первой версии

Индексируется один проект: `<indexed-project>` — 719 файлов `.cs`, 3.9 МБ исходников (без `bin`/`obj`). Выбран потому, что правила этого проекта требуют сверяться с его исходниками при каждой задаче, то есть выигрыш будет максимальным и сразу заметным, а код стабилен — редкие перестройки индекса.

Путь к проекту — параметр конфигурации, не константа. Кэши разных проектов изолированы, так что расширение на другие репозитории не потребует изменения кода.

## 3. Целевое окружение

| Компонент | Значение |
|---|---|
| GPU | NVIDIA RTX 5070 Ti, 16 ГБ VRAM |
| RAM | 64 ГБ |
| CPU | Intel i5-11400F, 6C/12T |
| Рантайм | .NET 10 |
| Эмбеддинги | Ollama, `qwen3-embedding:4b` |

`qwen3-embedding:8b-fp16` **не подходит**: 8B параметров в fp16 занимают около 16 ГБ, то есть всю VRAM без запаса на контекст. Берётся `qwen3-embedding:4b` — примерно 8 ГБ, остаётся место под другие задачи.

Родная размерность модели — 2560. Модель обучена с Matryoshka Representation Learning, поэтому вектор усекается до **1024 измерений** с потерей качества в единицы процентов и сокращением объёма кэша и времени поиска в 2.5 раза. Размерность вынесена в конфиг.

## 4. Архитектура

```text
<repo>\
├── src\
│   ├── CodeIndex.Core\              # логика, без зависимостей от MCP
│   │   ├── Sources\       ISourceProvider.cs, FileSystemSourceProvider.cs
│   │   ├── Chunking\      RoslynChunker.cs, CodeChunk.cs, FallbackChunker.cs
│   │   ├── Embedding\     IEmbeddingClient.cs, OllamaEmbeddingClient.cs
│   │   ├── Storage\       IndexStore.cs, IndexHeader.cs, ChunkManifest.cs
│   │   ├── Indexing\      IndexBuilder.cs, FileScanner.cs, FileFingerprint.cs
│   │   └── Search\        VectorSearcher.cs, SymbolMatcher.cs, HybridRanker.cs
│   └── CodeIndex.Server\            # stdio MCP-хост, определения инструментов
└── tests\
    ├── CodeIndex.Core.Tests\
    └── CodeIndex.Server.Tests\
```

`CodeIndex.Core` не знает о протоколе MCP. Это даёт тестируемость без поднятия хоста и возможность переиспользования из CLI, если позже понадобится.

`CodeIndex.Server` — тонкий слой: конфигурация, DI, четыре определения инструментов. Структура повторяет существующие MCP-серверы пользователя (`x-mcp`, `telegram-mcp`).

### ISourceProvider

Ни один класс за пределами `Sources` не обращается к `File` и `Directory` напрямую. Доступ к исходникам идёт через интерфейс: перечислить файлы проекта, прочитать содержимое, прочитать диапазон строк.

Единственная реализация в этой версии — `FileSystemSourceProvider`. Абстракция вводится не ради облака, а потому что окупается сразу: чанкер и индексатор тестируются на наборе файлов из памяти, без временных папок и мусора на диске. Побочный эффект — позже сюда можно подставить провайдер, читающий из клона репозитория на сервере, не трогая остальной код.

## 5. Чанкинг

Единица индексации — **член типа** (метод, свойство, конструктор, поле), а не файл целиком. Один вектор на файл размывает смысл: у крупного сервиса на две тысячи строк усреднённый вектор либо всплывает на любой запрос, либо теряется на всех.

Разбор через Roslyn (`Microsoft.CodeAnalysis.CSharp`). Для каждого чанка сохраняются:

| Поле | Назначение |
|---|---|
| `FilePath` | Путь относительно корня проекта |
| `StartLine`, `EndLine` | Точные границы для перехода к коду |
| `Kind` | Method / Property / Constructor / Class / Interface / Enum / Record |
| `Symbol` | Полное имя, например `Xrpl.Client.XrplClient.AccountInfo` |
| `Signature` | Сигнатура с типами параметров и возвращаемым типом |
| `DocComment` | XML-документация, если есть |

Модели передаётся структурированный текст, а не голое тело метода:

```text
File: src/Xrpl/Client/XrplClient.cs
Namespace: Xrpl.Client
Type: XrplClient (class)
Member: Task<AccountInfoResponse> AccountInfo(AccountInfoRequest request)
Doc: Retrieves account root information for the given address.
Code:
<тело, обрезанное до ~2000 символов>
```

Так эмбеддинг получает и структурный сигнал (имена, типы, иерархия), и смысловой (тело, документация).

Объявление типа даёт отдельный чанк, содержащий только заголовок класса, его doc-комментарий и перечень членов — это позволяет находить «класс целиком», а не только отдельные методы.

Помимо методов, свойств и конструкторов индексируются операторы, операторы преобразования, индексаторы, события, делегаты, а из полей — только `const` и `static readonly`. Обоснование от замеров на `<indexed-project>`: индексаторы и операторы (`Amount operator *`, `Enumeration[string]`) образуют публичную поверхность API, по которой ищут, а делегаты вообще оставляли три файла полностью непроиндексированными. Обычные приватные поля исключены сознательно — их 1545, они попадают в перечень членов типа и отдельными чанками дали бы шум, тогда как константы протокола вида `public const string TransactionType = "Payment"` — ровно то, что ищут в SDK.

Сигнатура сохраняет модификаторы члена и параметров (`static`, `async`, `this`, `ref`, `out`, `params`): без них extension-метод неотличим от обычного статического, а такие слова — высокоценные поисковые токены. Ограничения `where` отбрасываются как шум.

Из doc-комментариев снимается вся XML-разметка с сохранением текста внутри тегов. На `<indexed-project>` 52.8% комментариев содержат `<param>`, `<returns>`, `<see cref>` и подобное, и без очистки половина документации уходила бы в эмбеддинг вместе с угловыми скобками.

**`Symbol` не уникален и не может служить ключом.** Замер: 125 значений повторяются, худший случай — `Xrpl.Models.Transactions.Validation` встречается 76 раз, поскольку `partial class` разложен по 76 файлам; перегрузки и дженерики разной арности схлопываются тоже. Это корректное поведение, но любой индекс обязан ключеваться составным `FilePath + Symbol + Kind + StartLine` либо порядковым номером чанка.

Если Roslyn не смог распарсить файл, применяется `FallbackChunker` — разбиение по строкам с перекрытием. Файл не должен теряться из индекса ни при каких обстоятельствах.

## 6. Хранилище

Расположение: `%LOCALAPPDATA%\code-index-mcp\<projectId>\`

`projectId` — короткий идентификатор из конфигурации (например, `myproject`), а **не** производная от абсолютного пути. Пользователь работает на двух машинах, где один и тот же репозиторий лежит по разным путям (например, `<path-A>\...` и `<path-B>\...`); привязка ключа к пути сделала бы кэш непереносимым между ними без всякой пользы.

Два файла:

- `manifest.json` — заголовок, метаданные чанков и отпечатки файлов
- `vectors.bin` — плотный массив `float32`, N × D, подряд, без заголовка и разделителей

Метаданные хранятся текстом, потому что при девяти тысячах чанков это порядка двух мегабайт, а возможность открыть файл глазами при разборе проблемы стоит дороже экономии. Векторы — бинарно и без заголовка: тогда чтение не требует арифметики смещений, а корректность длины проверяется сверкой с `ChunkCount × Dimensions × 4` из манифеста.

Чтение векторов — `MemoryMarshal.Cast<byte, float>` поверх прочитанного буфера. Это zero-copy: поэлементное копирование не выполняется вообще.

> **Обязательное требование.** Поэлементные циклы по элементам векторов запрещены — ни при чтении, ни при записи, ни при вычислении similarity. При 9000 чанков и 1024 измерениях это 9 млн итераций, что на интерпретируемом коде даёт задержки в десятки секунд. Только блочные операции и SIMD.

### Заголовок

`IndexHeader` содержит magic-сигнатуру, версию схемы, имя модели, размерность, количество чанков и время сборки. Любое несовпадение модели или размерности означает полную пересборку — искать по векторам, посчитанным другой моделью, недопустимо, причём молча и без падения.

## 7. Поиск

Гибридный, две ветки со слиянием.

1. **Векторная ветка.** Эмбеддинг запроса, косинусное сходство со всеми векторами через `System.Numerics.Tensors.TensorPrimitives.CosineSimilarity` (SIMD). Топ-50.

2. **Символьная ветка.** Совпадения по `Symbol` и `Signature`. Нужна потому, что чистая семантика плохо обрабатывает запросы вида «где `TrustSetFlags`» — точное имя идентификатора для эмбеддинга слабый сигнал. Топ-50.

3. **Слияние — Reciprocal Rank Fusion:** `score = Σ 1/(60 + rank)` по обеим веткам. Выбран потому, что не требует подбора весов между разнородными шкалами (косинус и текстовая релевантность несопоставимы напрямую) и устойчиво работает без настройки.

4. Возврат топ-K, по умолчанию 10.

**Почему brute-force, а не HNSW или векторная БД.** При 9000 векторов по 1024 измерения полный перебор — примерно 9 млн умножений с накоплением, что на SIMD занимает единицы миллисекунд. ANN-индексы начинают окупаться от сотен тысяч векторов, а до того лишь добавляют зависимость, погрешность и код построения графа. `sqlite-vec`, Qdrant и подобное в этом проекте не используются.

### Асимметричное кодирование: инструкция только для запроса

Принятое (по измерению, не по вкусу) проектное решение: документы (чанки кода) кодируются как есть, запрос — с добавленным префиксом. Qwen3-Embedding, как и другие модели E5/GTE-семейства, обучена асимметрично: пассаж эмбеддится напрямую, а запрос ожидается в виде `Instruct: {задача}\nQuery: {запрос}`. До этого решения обе стороны кодировались одинаково — запрос эмбеддился точно так же, как чанк, — что не соответствует тому, как модель обучалась.

Решение зафиксировано измерением на тех же семи контрольных запросах, что и в п. 12 (`<indexed-project>`, каждый результат сверен с реальным кодом по указанным строкам, а не принят по правдоподобному имени символа):

| | Без префикса | С префиксом (принято) |
|---|---|---|
| Верно в топ-3 | 4 из 7 | 7 из 7 (6 из них — 1-е место) |

Без префикса три запроса были слабыми: один явный промах («how is a payment transaction signed» возвращал код конверта X402 вместо `Xrpl/Wallet/XrplWallet.cs`) и два «рядом, но не то» (retry-логика и жизненный цикл websocket-соединения находились, но не на вершине выдачи). С префиксом все три ушли на 1-е место, кроме сигнатуры платежа — там `XrplWallet.ComputeSignature` теперь 3-й (1-е место — интеграционный тест, вызывающий ту же подпись); это зафиксировано как есть, без округления до «ранг 1».

Префикс применяется исключительно к `IEmbeddingClient.EmbedQueryAsync` (настройка `EmbeddingOptions.QueryInstruction`) и никогда — к тексту чанка при индексации: смешение его в индексацию свело бы на нет саму асимметрию, ради которой модель обучалась, и потребовало бы полной переиндексации. Поэтому изменение `QueryInstruction` **не требует перестройки индекса** — в отличие от смены `Model` или `Dimensions`, которые меняют то, что реально хранится в `vectors.bin`.

Рассматривались, но не применялись (префикс сам закрыл разрыв, а оба варианта дороже) два следующих кандидата: поднять `Dimensions` до нативных для модели 2560 (переиндексация, кэш вырастет примерно до 92 МБ) и перейти на `qwen3-embedding:8b` (ещё 2.5 ГБ загрузки, переиндексация, больше VRAM).

## 8. Инкрементальное обновление

Стратегия — проверка перед каждым поиском. Индекс не может устареть.

Отпечаток файла — размер и `LastWriteTimeUtc`. Если оба совпали с манифестом, файл не трогаем. Если разошлись — считается хэш содержимого, и только при его изменении файл переиндексируется.

Хэш обязателен, потому что `git checkout` меняет время модификации, не меняя содержимое. Без этой проверки каждое переключение ветки вызывало бы полную перестройку.

Удалённые файлы вычёркиваются из манифеста, `vectors.bin` уплотняется.

Полное сканирование 719 файлов занимает доли секунды, поэтому накладные расходы на проверку перед каждым запросом пренебрежимы.

## 9. Инструменты MCP

| Инструмент | Параметры | Возвращает |
|---|---|---|
| `code_search` | `query`, `limit` (10), `kind?`, `pathFilter?` | `id` чанка, путь, диапазон строк, сигнатура, doc и первые ~15 строк тела |
| `code_get_chunk` | `id` | Полное тело члена — дешевле, чем читать файл целиком |
| `code_index_status` | — | Число чанков, время сборки, модель, размерность |
| `code_reindex` | `force` | Принудительная пересборка |

`id` в выдаче `code_search` обязателен — без него нечего передать в `code_get_chunk`.

Тела чанков **не хранятся** в кэше. И фрагмент в выдаче `code_search`, и полное тело в `code_get_chunk` читаются с диска по `FilePath` и диапазону строк в момент запроса. Это держит кэш компактным (только векторы и метаданные) и гарантирует, что выдаётся актуальный код, а не снимок на момент индексации. Корректность диапазонов строк обеспечивается проверкой свежести из раздела 8, которая выполняется до поиска.

Формат выдачи `code_search` выбран как компромисс: только путей и строк недостаточно — почти всегда потребуется дочитывать файлы, и суммарно выйдет дороже; полные тела десяти членов легко дают тысячи токенов и обесценивают всю затею. Сигнатуры с фрагментом обычно хватает, чтобы понять, тот ли это код, а за подробностями есть `code_get_chunk`.

## 10. Обработка ошибок

Принцип — деградация, а не отказ.

| Ситуация | Поведение |
|---|---|
| Ollama не запущен | Работает только символьная ветка; в ответе явное предупреждение и подсказка `ollama serve` |
| Индекс отсутствует | Первый вызов строит его, прогресс через MCP-логирование |
| Заголовок не совпал (модель, размерность, версия схемы) | Полная пересборка |
| `vectors.bin` обрезан или размер не кратен `D × 4` | Внятное исключение, затем пересборка |
| Файл не парсится Roslyn | `FallbackChunker`, файл остаётся в индексе |
| Модель не найдена в Ollama | Ошибка с точной командой `ollama pull` |

## 11. Тестирование

TDD. Пакеты: `xunit.v3`, `xunit.runner.visualstudio`, `Microsoft.NET.Test.Sdk`, `coverlet.collector`. Всё.

Библиотеки ассертов не используются — только встроенный `Assert`. `FluentAssertions` с версии 8.0 перешла на платную для коммерческого использования лицензию Xceed, а фиксация на 6.11.0 в существующих репозиториях — вынужденное legacy, которое не тиражируется в новый код.

`Moq` также не используется: единственное место, где нужен мок — HTTP-клиент Ollama, и там достаточно самописного `FakeHttpMessageHandler` на полтора десятка строк, возвращающего заданный JSON. Это прозрачнее и убирает вторую запиненную зависимость.

Состав:

- **`RoslynChunker`** — вложенные классы, `partial`, `record`, file-scoped namespaces, top-level statements, generic-методы. Проверяются границы строк и полное имя символа.
- **`IndexStore`** — round-trip записи и чтения побайтово идентичен; обрезанный файл и чужая размерность дают исключение, а не тихую порчу выдачи.
- **`FileFingerprint`** — смена времени модификации без изменения содержимого не вызывает переиндексацию.
- **`HybridRanker`** — RRF на фикстурах с заранее известным ожидаемым порядком.
- **`OllamaEmbeddingClient`** — на `FakeHttpMessageHandler`: батчинг, отказ соединения, усечение вектора до 1024.
- **Интеграционный** — синтетический мини-проект и набор эталонных запросов; каждый обязан вернуть нужный член в топ-3. Единственный тест, измеряющий качество поиска, и потому главный.

|---|---|---|
| Чанков из 719–723 файлов | 6 000 – 9 000 | 8 735 |
| Первая индексация | 4 – 8 минут | 451.6 с (≈ 7.5 мин) |
| Размер кэша при D=1024 | ~35 МБ | 36.7 МБ |
| Проверка актуальности (`RefreshAsync`, без изменений) | < 1 с | 0.16 с |
| Время поиска | < 100 мс | **см. ниже — оценка была неверной** |

**Оценка времени поиска не подтвердилась.** Прогнозировавшиеся «< 100 мс» предполагали только время самого векторного поиска и не учитывали, что каждый запрос сперва должен получить эмбеддинг от Ollama — а это доминирующая часть стоимости.

Реально запрос стоит **около 200 мс**: примерно 190 мс на эмбеддинг запроса в Ollama плюс порядка 1.6 мс на сам поиск по индексу (8735 векторов, D=1024). Эти 200 мс — цифра для **прогретой** модели, то есть уже загруженной в VRAM. Она справедлива только пока модель резидентна.

Если модель не резидентна, картина другая — измерено прямыми вызовами к `POST /api/embed`:

| Вызов | Латентность |
|---|---|
| Холодный (модель не в памяти) | 12 057 мс |
| Второй сразу после холодного | 2 795 мс |
| Прогретый (стабильное состояние) | 191 мс |

Ollama выгружает модель из VRAM по умолчанию через 5 минут простоя (`keep_alive`). При реалистичном темпе работы — запрос раз в 5–10 минут — без вмешательства **каждый** запрос платил бы 12-секундную холодную загрузку, что медленнее `Grep` и обнуляет весь смысл индекса. Решение — `EmbeddingOptions.KeepAlive` (по умолчанию `"30m"`), передаваемый в `keep_alive` каждого запроса к `api/embed`: модель остаётся резидентной на всё рабочее окно поиска и не удерживает 10 ГБ VRAM бессрочно.

## 13. Интеграция

Регистрация stdio-сервера в конфигурации MCP. В `CLAUDE.md` индексируемого проекта добавляется правило: для поиска по его коду использовать `code_search`, а не `Grep`.

Второй пункт не менее важен первого. Инструмент, о котором забывают, экономии не даёт — а `Grep` остаётся поведением по умолчанию, пока явно не сказано иное.

## 14. Переносимость между машинами

Работа ведётся на двух ПК, где один и тот же репозиторий лежит по разным путям. Требование: индекс должен быть машинно-независимым.

Это обеспечивается тремя решениями, каждое из которых уже принято по другим причинам:

1. **Пути в манифесте относительные** (раздел 5) — кэш не содержит абсолютных путей или буквы диска.
2. **`projectId` вместо хэша пути** (раздел 6) — один и тот же ключ кэша на обеих машинах.
3. **Свежесть с откатом на хэш содержимого** (раздел 8) — после `git clone` или `git checkout` время модификации отличается у всех файлов, но содержимое совпадает, поэтому переиндексации не происходит.

В итоге кэш можно либо скопировать между машинами (около 35 МБ), либо просто пересобрать за несколько минут. Автоматическая синхронизация не реализуется: выигрыш от неё меньше стоимости поддержки, учитывая, что исходники и так синхронизируются через git.

## 15. Путь к облачному варианту

Доступ из облачных агентов заявлен как возможная будущая потребность, но не текущая. Сейчас он **не реализуется** — облачный вариант это не другой транспорт, а другой продукт: серверу нужен доступ к рабочей копии, а значит загрузка снимка репозитория, его инвалидация, вопросы приватности исходников и аренда GPU под инференс. Строить это до появления реальной необходимости — угадывание требований.

Чтобы дверь оставалась открытой, соблюдаются три ограничения:

- `CodeIndex.Core` не ссылается на пакеты MCP — транспорт подключается сверху.
- Доступ к файлам только через `ISourceProvider` — серверная реализация подставляется без изменений в чанкере, индексаторе и поиске.
- Вычисление эмбеддингов только через `IEmbeddingClient` — Ollama можно заменить на удалённый эндпоинт или облачный embeddings-API, оставив индекс локальным. Это же покрывает случай машины без подходящей GPU.

Ничего сверх этих трёх пунктов ради гипотетического облака не закладывается.

## 16. Вне области (YAGNI)

- ANN-индексы, HNSW, векторные БД
- Нейросетевой реранкер второй ступени
- Индексация файлов, кроме `.cs`
- HTTP-транспорт, веб-интерфейс, аутентификация
- Загрузка снимков репозитория на сервер
- Автоматическая синхронизация кэша между машинами
- Индексация нескольких проектов одновременно

## 17. Критерии приёмки

1. Индекс `<indexed-project>` строится с нуля одной командой, без ручных шагов кроме установки Ollama и загрузки модели.
2. `code_search` по эталонному набору запросов возвращает нужный член в топ-3.
3. Повторный поиск без изменений в коде отрабатывает быстрее секунды.
4. Изменение одного файла вызывает переиндексацию только этого файла.
5. Переключение ветки git без изменения содержимого не вызывает переиндексацию.
6. Остановленный Ollama не ломает инструмент — символьный поиск продолжает работать.
7. Кэш, скопированный с другой машины, где репозиторий лежит по иному пути, принимается без переиндексации.
8. Ни один класс вне `Sources` не обращается к `File` или `Directory` напрямую.
9. Все тесты проходят.
