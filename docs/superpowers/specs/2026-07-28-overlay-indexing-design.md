# Overlay-индексация: база + оверлеи вместо повторного эмбеддинга при переключении веток

**Дата:** 2026-07-28
**Статус:** дизайн утверждён, реализация выполнена в этой же сессии
**Связанные файлы:** `src/CodeIndex.Core/Indexing/IndexBuilder.cs`, `src/CodeIndex.Core/Storage/*`, новый namespace `src/CodeIndex.Core/Overlays/*`

## 1. Проблема

Сегодня один индекс на проект, обновляемый инкрементально (`IndexBuilder.RefreshAsync`). `FileFingerprint` уже умеет отличать «изменился таймстамп, но не содержимое» (случай `git checkout` на то же самое дерево) от настоящего изменения — но только когда содержимое совпадает с тем, что **сейчас лежит на диске**. Если ветка реально отличается (например 389 файлов из 8000), переключение на неё вызывает переэмбеддинг этих 389 файлов, а переключение обратно — переэмбеддинг тех же 389 файлов ещё раз, потому что первое переключение перезаписало их эмбеддинги на диске. Работа выбрасывается на каждом свиче.

Эталонная схема (по описанию задачи) — неизменяемая база плюс компактные оверлеи на ветку: база — замороженное поколение, оверлей хранит только отличающиеся файлы, поиск компонует их, маскируя записи базы по пути. Ветка, трогающая 389 файлов, платит за 389 — один раз.

## 2. Четыре решения

### 2.1. Что ключует оверлей

**Решение: контент-ключ, не git.** Оверлей ключуется хэшем (XxHash3, как и `IndexStore.VectorsHash`) от детерминированной сериализации: отсортированный список `(relativePath, contentHash)` для каждого файла, отличающегося от базы (добавлен/изменён) + отсортированный список путей, удалённых относительно базы.

Почему не git, хотя это и есть «эталонная» реализация:

- В проекте сегодня **нет** зависимости от git ни в одном классе — весь доступ к исходникам идёт через `ISourceProvider`/`FileSystemSourceProvider`, работающие с произвольной директорией, включая git worktree без `.git`, копию репозитория без истории, или вообще не-git каталог (см. `README.md`/`ProjectOptions.Root` — путь просто директория). Требование задачи прямо просит не ломать эти случаи.
- Если бы каталог не был git-репозиторием (или git недоступен в PATH), ключевание по дереву коммита отказало бы полностью — потребовался бы fallback-путь всё равно, то есть два механизма вместо одного.
- Контент-ключ работает одинаково для git-репозитория, worktree, обычной папки — `IndexBuilder` уже вычисляет `FileFingerprint.ContentHash` для каждого изменившегося файла как часть обычного инкрементального прохода (см. `AnyFileNeedsAttentionAsync` → `ReadTextAsync` → `ComputeHash`), так что довычислить оверлейный ключ — это агрегация уже вычисленных хэшей, а не новый дорогой проход.
- Побочный плюс контент-ключа: он **дедуплицирует** идентичные по содержимому состояния под разными именами веток (rebase, cherry-pick на два разных бренча дающие байт-в-байт одинаковое дерево переиспользуют один оверлей) — git-commit-ключ этого не даёт (разные SHA при одинаковом дереве).
- Минус: без git нельзя мгновенно понять «сколько файлов отличается» без разбора содержимого — но это уже делает существующий `RefreshAsync` каждый вызов (дешёвый stat-проход), overlay-логика лишь переиспользует его результат.

### 2.2. Сколько оверлеев хранить и как вытеснять

**Решение: ограниченный пул, по умолчанию 8 слотов (`CodeIndexOptions.MaxOverlays`, настраивается), вытеснение LRU по `LastUsedUtc`.**

Оверлей хранит только diff от базы (обычно десятки–сотни чанков, не тысячи), так что даже 8 оверлеев стоят разумных мегабайт, а не долю полного индекса. При создании нового оверлея, если пул полон — вытесняется слот с наименьшим `LastUsedUtc` (директория `overlays/<slotId>/` удаляется, запись в `registry.json` убирается). Активный оверлей никогда не вытесняется сам собой (он и есть самый недавно использованный).

Отдельного вытеснения по суммарному размеру не введено: реальный диапазон размеров оверлея (diff от базы) настолько мал по сравнению с полным индексом, что счётный лимит уже ограничивает и байты на практике; если ветка отличается от базы почти полностью, соответствующий оверлей будет большим один раз, и это ожидаемо и корректно (это и есть honest cost такого различия), а не патология, которую нужно предотвращать отдельным механизмом.

### 2.3. Как id чанка переживает композицию

**Решение: персистентный счётчик `CompositionGeneration` в `registry.json`, не число из `IndexHeader` базы или оверлея по отдельности.**

`ProjectChunkId` уже несёт `Generation` именно для того, чтобы протухший id обнаруживался, а не тихо резолвился не в тот чанк (см. `StaleChunkIdException`). Композиция (база, маскированная активным оверлеем) пересобирает плоский список чанков в порядке путей заново при каждом вызове — если бы `Header.Generation` результата брался из базы или из оверлея «как есть», два разных активных оверлея с совпавшим (случайно) внутренним поколением дали бы одинаковый `Generation` при разных фактических раскладках ординалов — ровно та тихая ошибка, которую `Generation` должен ловить.

Правило: `CompositionGeneration` увеличивается на 1 и сохраняется в `registry.json`, когда **либо** форма списка чанков активного слоя меняется (тот же критерий, что и сегодня в `IndexBuilder` — последовательность `(путь, число чанков)`), **либо** активный слот меняется (переключились на другой оверлей или на голую базу), даже если по случайному совпадению форма осталась той же. Возвращаемый `IndexSnapshot.Header.Generation` — всегда это персистентное значение, не то, что вычислил внутренний `Assemble` для промежуточного шага. Значение переживает перезапуск процесса (пишется в `registry.json` рядом со списком слотов), так что оно валидно и для сценария «MCP-клиент стартует новый процесс сервера каждую сессию» — тот же принцип, что уже документирован для `IndexHeader.Generation` сегодня.

### 2.4. Двигается ли база

**Решение: база продолжает обновляться на месте для *небольших* изменений (ровно как сегодня, без каких-либо оверлеев вообще) и полностью сбрасывается (со всеми оверлеями) только на явный полный ребилд (`RebuildAsync`).**

Это то решение, которое напрямую отвечает за требование «проект без переключения веток ведёт себя ровно как сейчас, без лишних файлов на диске»: обычная разработка на одной ветке — это один-два файла, изменившихся между двумя вызовами `RefreshAsync` (он гоняется перед каждым поиском), что **всегда** ниже порога активации оверлея (см. §3) → `overlays/` не создаётся вообще, база просто дописывается на месте как и раньше.

Оверлеи не инвалидируются дрейфом базы: каждая запись оверлея самодостаточна (путь, хэш содержимого, чанки, векторы), так что для путей, которых оверлей не переопределяет, композиция берёт **текущую** (возможно, более свежую) версию из базы — это корректно и желательно: если пока вы сидели на feature-ветке кто-то доработал `main` в файле, которого feature не касается, вы хотите видеть свежую версию `main`, а не замороженную на момент создания оверлея.

Единственное, что сбрасывает все оверлеи — явный `RebuildAsync` (полный ребилд с нуля): он уже дорогая, редкая, осознанная операция; передоверять всем существующим оверлеям валидность относительно нового состояния базы небезопасно (могла измениться конфигурация расширений, структура дерева и т.д.), поэтому `overlays/` полностью удаляется при ребилде — самое простое и надёжное правило.

## 3. Порог активации оверлея

Без git нет бесплатного сигнала «это переключение ветки», так что используется явная эвристика: если очередной `RefreshAsync` обнаруживает **больше `OverlayActivationThreshold` файлов**, нуждающихся во внимании (добавлен/удалён/не совпал по stat), за один проход — это трактуется как «дивергенция» и запускается оверлейная логика (поиск подходящего кэшированного оверлея по контент-ключу, либо создание нового). Если файлов меньше порога — это обычное обновление активного слоя на месте (сегодняшний алгоритм, без изменений).

По умолчанию `OverlayActivationThreshold = 10` (настраивается). Обоснование: между двумя последовательными поисковыми запросами (а `RefreshAsync` гоняется перед каждым) обычная разработка меняет 1 файл, изредка несколько — переключение ветки, различающейся на сотни файлов, всегда далеко за порогом. Явный компромисс: очень маленькая ветка (2-3 файла) не активирует оверлей и просто переэмбеддится каждый раз как раньше — это приемлемо, так как цена такой ветки и так мала (это и есть весь смысл порога — не платить оверлейной бухгалтерией за то, что дешевле сделать напрямую).

## 4. Устройство хранилища

```
<cacheDir>/
  manifest.json, vectors.bin        # база — тот же формат/путь, что и сегодня, IndexStore не менялся
  overlays/                          # создаётся лениво, только при первой дивергенции
    registry.json                    # список слотов + ActiveSlotId + CompositionGeneration
    <slotId>/
      manifest.json                  # только переопределённые файлы: chunks, fingerprints, deletedPaths, contentKey
      vectors.bin                    # векторы только для чанков из этого оверлея
```

Проект, ни разу не разошедшийся с базой, не создаёт `overlays/` вообще — «no branch switching → no extra files» выполняется буквально.

## 5. Компоненты (namespace `CodeIndex.Core.Overlays`)

- `OverlaySnapshot` — данные одного слота в памяти (contentKey, переопределённые fingerprints/chunks, deletedPaths, векторы).
- `OverlayStore` — персистентность одного слота (temp+rename, тот же паттерн, что `IndexStore`).
- `OverlayRegistryDocument` / `OverlayRegistry` — чтение/запись `registry.json`, выделение/вытеснение слотов.
- `OverlayComposer` — чистые функции: `Compose(base, overlay?) → IndexSnapshot`, `ExtractDiff(base, updated) → overlay data`, `ComputeContentKey`, `HasShapeChanged`, `CountFingerprintDiff`.
- `OverlayIndexBuilder : IIndexBuilder` — оркестратор: держит `_baseSnapshot`/`_registry`/`_activeOverlay` в памяти, переиспользует существующий `IndexBuilder` через новый internal-метод `ComputeRefreshAsync(ct, current, persist)` (тот же алгоритм диффа/пересборки, что и сегодняшний `RefreshAsync`, только с управляемым сохранением) — это единственное изменение в `IndexBuilder`: приватное тело `RefreshAsync` вынесено в `internal` метод с параметром `persist`, публичный `RefreshAsync` вызывает его с `persist: true` — поведение и все существующие тесты не меняются побитово.

`CodeIndexService` теперь принимает `IIndexBuilder` вместо конкретного `IndexBuilder` (интерфейс с теми же тремя методами) — единственное изменение в публичном API `Core`. `ProjectRegistry` конструирует `OverlayIndexBuilder`, оборачивающий обычный `IndexBuilder`, когда оверлеи включены (по умолчанию включены), иначе — обычный `IndexBuilder` напрямую, что даёт байт-в-байт прежнее поведение при `EnableOverlays = false`.

## 6. Что сознательно не сделано (YAGNI)

- **Кросс-оверлейная дедупликация по отдельным файлам.** Если ветка B отличается от базы файлами {X,Y,Z}, а ветка C — файлами {X,Y,W}, и X/Y совпадают по содержимому в обеих — сейчас они хранятся в обоих оверлеях независимо (не переиспользуются друг из друга). Даёт небольшой лишний диск ради простоты и предсказуемости; полноценный контент-адресуемый кэш на уровне файла — отдельная, более сложная работа, не оправданная измеренным выигрышем (см. §7).
- **Вытеснение по размеру** — не введено отдельно от количества слотов (см. §2.2).
- **Автодетект «это именно git-branch switch»** — не делается; используется файловая эвристика по порогу (см. §3), не anything git-specific.

## 7. Измеренный эффект

Измерено на реальном индексе `xrplcsharp` (766 файлов, 8897 чанков, `qwen3-embedding:4b`, 1024 измерения). Создана scratch-ветка `scratch/overlay-bench` от `dev`, отличающаяся 150 файлами (дописана безвредная строка-комментарий в конец каждого — меняет контент-хэш и вызывает переэмбеддинг всех чанков файла, не меняя структуру кода). Кэш предварительно скопирован в две независимые копии (baseline / overlay), реальный кэш пользователя не трогался.

| Шаг | Без оверлеев | С оверлеями |
|---|---|---|
| `dev` (no-op) | 0.30 с, 0 чанков | 0.27 с, 0 чанков |
| → `scratch` (1-й раз) | 85.16 с, **1951** чанк | 79.82 с, **1951** чанк (создаётся оверлей) |
| → `dev` (назад) | 82.40 с, **1951** чанк | **0.28 с, 0 чанков** |
| → `scratch` (2-й раз) | 82.02 с, **1951** чанк | **0.28 с, 0 чанков** |
| Итого 3 переключения | ~249.6 с, 5853 чанка | ~80.4 с, 1951 чанк (один раз) |

Оверлей для 150 файлов (около 1951 чанка) занял на диске **8.53 МБ** — против **39.1 МБ** полного индекса, то есть ~22% от размера всего проекта за diff почти в 20% файлов репозитория (150 из 766) — пропорция ожидаемая и не патологическая.

Вывод: для ветки, реально отличающейся на заметную долю файлов, оверлеи убирают повторный переэмбеддинг практически полностью (с 82 с и 1951 чанка до 0.28 с и 0 чанков на каждый повтор) — выигрыш растёт линейно с числом раз, когда пользователь возвращается к уже виденному состоянию. Сложность реализации (см. §5) оправдана этим результатом: именно повторные переключения между небольшим числом веток — основной сценарий использования, который и назван в задаче.
